# GridTalk 协议分层设计说明

GridTalk 是 STM32F411 双板系统（`MX_autoMata` 控制器 / `MX_remoteControlPad` 遥控器）
使用的无主机多对多半双工串行总线协议。单跳共享总线不存在路由，因此不设网络层，
按经典物理/链路/应用三层组织。全部状态封装在 `gridTalk_t` 结构体内（多实例），
平台通过钩子接入时间源、发送输出和应用回调。

```
┌─ L3 应用层: 命令语义(CMD分发) · onRx/onSendResult · send/sendReply/sendNoAck · 多实例
├─ L2 链路层:
│   ├─ 帧: 定界(FF 00/FF FE/FF FF转义) + 寻址(目标ID+源ID) + Fletcher-16 + 应答(FF FC+目标ID)
│   ├─ 媒体访问: 空闲判定(自主4.5字符) / 应答4字符时限 · 接入与退避
│   └─ 可靠性: ACK队列+优先 · 超时重发 · 去重 · 半双工回显过滤
└─ L1 物理层: UART驱动 · 字节速率自适应测量
```

> 分层修正说明：寻址（目标/源 ID）是链路层职责（决定是否收下、应答回给谁），
> 下放至 L2；媒体访问/应答/重发/去重本就是数据链路层（MAC+LLC），不再单列高层。

## L1 物理层

### 设计要点
- 半双工共享总线：发送期间（含最后一字节移位尾巴）忽略接收，过滤自身回显与冲突噪声；
- **自适应字节速率**：只采样"帧内字节间隔"（第 2 字节起），得到实测 `byteUs`，
  发送节流、空闲判定、退避窗口全部以它为单位；
- **事件驱动排空**：`send / rxByte / usTick` 任一入口都会立即驱动发送状态机，
  不再依赖"每 1ms tick 发 1 字节"；
- 平台钩子：`nowUs`（µs 时钟，真机用 DWT 自由计数器）、`txByte`（发送输出）、
  `uart`（寄存器直写）。

### 面临的问题
1. 固定 1ms tick 逐字节发送 → 速率只有 ~500B/s，响应首字节还要等下一个 tick；
2. 波特率配置偏差 → 固定字节时间不匹配；
3. 半双工回显会把自己发的帧喂回解析器。

### 解决办法
1. 事件驱动排空 + 按实测 `byteUs` 节流（配合硬件 TXE），达到线速；
2. 帧内间隔采样自适应 `byteUs`；
3. 半双工窗口过滤：发送中或最后一字节未移出时丢弃 RX。

## L2 链路层

### 帧（定界 + 寻址 + 校验 + 应答）

#### 设计要点
- 定界：`FF 00` 起始，`FF FE` 结束；帧内 `FF` 转义为 `FF FF`；
- **寻址：目标 ID(2) + 源 ID(2) 置于帧头**，链路层据此决定是否收下、应答回给谁；
- 校验：Fletcher-16（模 255），覆盖全帧（含广播）；
- 应答：`FF FC` + 2 字节目标 ID（仅目标节点确认）。

#### 面临的问题
1. 帧内出现 `FF` 会破坏定界；
2. 坏帧/半帧会卡死解析状态；
3. 无地址 ACK 会被总线上所有等待者误收（假成功）。

#### 解决办法
1. `FF` 转义成 `FF FF`；
2. 接收字节间隔超时复位 + 帧内非法序列立即丢弃重同步；
3. 应答带目标 ID，仅 ID 匹配且处于等待状态才确认；解析 ACK 的残留状态在
   发送/超时后复位，避免吃掉下一帧开头。

### 媒体访问

#### 设计要点
- 无主机多对多：所有节点地位平等；
- **空闲判定**：自主发送前要求总线静默 ≥ `GT_IDLE_CHARS_X10/10`（默认 4.5）字符时间，
  再随机退避 `0..GT_AUTO_BACKOFF_CHARS-1` 字符；
- **应答时限**：收到帧后须在 `GT_REPLY_WINDOW_CHARS`（默认 4）字符时间内开始回复，
  实际用 `GT_REPLY_START_CHARS`（默认 2）字符就绪即发（快速通道，不做退避）。

#### 面临的问题
1. **盲窗碰撞**：设备开始发送后约 1 字符内别人听不到，两台同时起步必撞；
2. 固定/过大的接入抖动 → 排队拥塞，反而更差。

#### 解决办法
1. 静默间隔（4.5 字符）+ 随机短退避，把盲窗碰撞率压到 1% 以内；
2. 应答走 1 字符快速通道（满足 4 字符时限），自主帧才做退避。

### 可靠性（ACK / 重发 / 去重）

#### 设计要点
- ACK 队列（16）+ 绝对优先（可抢占等待/退避状态，发完恢复）；
- 单播带地址 ACK + 超时指数退避重发（窗口按实测 `byteUs`）；广播/NoAck 尽力而为；
- 重复帧去重表（16 槽，按源分槽）。

#### 应答超时（自适应，只等 ACK）
- 超时 = **本帧实测发送时间 + `GT_ACK_WINDOW_CHARS`（默认 60）字符**，
  随波特率/帧长自适应，发送完成时才启动计时；等待对象是 **4 字节 ACK**
  （`FF FC + 目标ID`，快速通道），窗口余量覆盖 ACK 队列排队；
- **ACK 与数据返回是两次独立传输**：接收方先回 ACK（L2 确认），应用层如需返回数据，
  由接收方再单独发一帧（如回声 0x0501），该帧自己走 ACK+超时重发，不占发送方的
  ACK 窗口；
- 固定超时（旧 400ms）在大帧（如 2KB 分片的 512B 帧，9600 波特下发送就要 ~618ms）
  上会提前超时，重发的又是同帧 → 接收端去重表丢弃 → 发送端永远等不到应答，死锁；
- 小帧超时约 12~26ms（60 字符窗口），仍远低于旧 400ms，不会拖慢最小传输延迟；
- 重试计数只在取**新帧**时清零（修复 WAIT_ACK 内清零导致的"永不失败"假象）。

#### 面临的问题
1. ACK 互等死锁：所有设备都卡在等自己帧的 ACK 而不回别人的 ACK；
2. ACK 单槽覆盖：接收端忙时连续收帧，后帧覆盖前帧的应答目标；
3. 固定范围重发退避 → 高负载下重发互相碰撞形成级联；
4. 帧完成判定依赖 TC 寄存器/固定时间，时序不稳；
5. 去重单槽会被多源交错覆盖，重发帧被重复派发。

#### 解决办法
1. ACK 绝对优先：无论处于等待/退避，先回 ACK 再继续自己的帧；
2. ACK 队列 16 槽逐一回；
3. 指数退避（20→200 字符窗口）+ 重发前复查总线；
4. 帧完成判定 = "环形缓冲空 + 最后一字节已移出（实测字节时间）"，不依赖 TC；
5. 按源地址分槽去重，窗口 10s（须大于最长重发周期）。

## L3 应用层

### 设计要点
- 命令语义：CMD + 载荷经 `onRx` 分发给应用；
- `gridTalk_t` 结构体封装全部状态，一份代码任意实例数；
- 平台钩子：`nowUs` / `txByte` / `onRx` / `onSendResult`；
- 每实例独立 RNG（xorshift），替代共享 `rand()`；
- 发送分三类：`gridTalk_send`（自主可靠）、`gridTalk_sendReply`（响应，立即接入）、
  `gridTalk_sendNoAck`（尽力而为，轮询/探测用）。

### 面临的问题
1. 全局单例无法在同进程创建多实例，仿真只能编译多份 + 符号重命名；
2. 共享 `rand()` 使相邻实例的退避相关（人为抬高碰撞）；
3. 回调/发送可能被中断打断。

### 解决办法
1. 结构体状态 + 钩子注入；
2. 实例内 xorshift，按 ID 播种；
3. 公开入口（send/rxByte/usTick）临界区保护（MCU 上为关中断）。

## 实测表现（6 台：1A 轮询 + 5B 单环，9600bps，2% 丢包）

| 指标 | 值 |
|---|---|
| 单跳最小（触发→下一台解析） | ~24ms ≈ 帧字节数+5 字节时间 |
| 单跳平均 | ~64~72ms |
| 碰撞帧占比 | <1% |
| 中继转发可靠 | 100%（0 失败） |
| 自适应字节时间 | 实测并跟随总线速率 |

## 仿真压测场景（tools/GridTalkSim）

### 场景组成
- 1 台 A：以 100ms/ID 后台轮询 1..255（前 N 台在线）；
- B 设备分组成中继环（默认 5 台/组，末组不足 5 台），组启动 500ms 错峰；
  B 收到中继帧延迟 1s 后转发给下一台，1→2→…→N→1 循环；
- C 设备（设备号 200）：随机目标向某 B 发送 2KB 随机数据，
  分片为 5×496B 帧（帧上限 512B），B 原样回声，C 校验序号+数据校验和；
  - 每片带随机 nonce，保证重发帧绕过接收端去重表（回声幂等）；
  - 数据传输用 `gridTalk_send`（可靠帧+ACK），**回声（0x0501）是 B 单独发起的
    独立传输**，由 B 侧 ACK+超时重发兜底；C 收到回声校验通过才发下一片；
  - C 侧另设回声事务超时（`ECHO_TXN_WINDOW_MS=15s`）：发片后窗口内未收到回声
    则同 seq 新 nonce 重发——ACK 到了但回声丢失（B 重发也失败）时不会卡死；
  - 分片索引只在回声校验通过后递增（修复早期"发送/回声双递增"导致的跳片 bug）。

### 200 台 + 0.5% 丢包（120s，3 个种子）
| 指标 | 结果 |
|---|---|
| 总线利用率 | 55~60%（已近饱和） |
| 碰撞损坏帧 | ~30%（帧vs帧为主） |
| 重发帧占比 | ~25% |
| A 轮询 | 3~4 个种子全部发现 199/199 台 |
| C 回声 | 修复后：3 次 2KB 全部 15/15 片真实校验通过、0 失败、事务超时重发 0 |
| 中继环 | 40 组中 13~18 组 0 圈；活跃组圈均 ~5.8s，单跳 avg 185~230ms / max 3.2s |

### 结论：200 台瓶颈是通道容量，不是协议缺陷
- 40 组连续中继（每圈约 2.4s 总线占用）+ 100ms 轮询 + 2KB 分片，超过 9600 半双工
  单信道可承载量；CSMA 在 55%+ 利用率下碰撞级联，饿死部分中继环；
- 对照实验（轮询 500ms + 错峰 2s + 转发延迟 3s）把利用率降到 38%，但仍有 8 组 0 圈，
  且 A 漏发现 5 台 —— 参数调优无法根治；
- 若要 200 台稳定：需降低并发中继（分时槽/更慢轮转）、提高波特率、
  或按需唤醒中继而非常驻循环。
